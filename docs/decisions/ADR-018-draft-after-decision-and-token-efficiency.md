# ADR-018: Draft the message after the human decision; merge explain and propose; limit the passages sent to the model

Status: Accepted (2026-10-10, P1.I2b.S7: S3 and S4 implemented and validated; the real-LLM token measurement of record is the author's run P1.I2b.S6)
Date: 2026-10-09

## Context

The first run with the real model (2026-10-08, `iteration-002.md`, "Showcase run") showed two problems with the Iteration 2 graph (detect, retrieve, explain, propose, draft, validate, human checkpoint, execute, audit):

1. **The draft is written for the proposed action, not for the human's action.** The draft node runs before the human checkpoint and writes the message for the policy action. When the approver chooses a different action (the run used return on an approve case), the message written for the proposal is sent unchanged. An approve needs no message at all, yet a draft is generated and paid for on every case.
2. **The token cost exceeds the free-tier budget.** Three structured calls per case used about 10,000 tokens (about 3,100 to 3,500 input tokens per call), more than the 8,000 tokens per minute of the default provider (ADR-016), so one case alone forces a retry. Most of the input is repeated across the three calls: the same system prompt, facts and retrieved passages, including passages outside the finding's own sections.

The human checkpoint, the code-owned policy (ADR-009), the "LLM never computes" rule (ADR-008) and the rule that explanation, proposal and draft always come from the LLM (AGENTS.md constraint 7) are not in question.

## Decision

- **Draft after the human decision.** The draft node moves after the human checkpoint and runs only when the human chooses return or escalate. It drafts the return message or the escalation note for the action the human chose, with the facts, the validated explanation and the human's choice as input. An approve produces no message and makes no draft call.
- **Second human step for the message.** The drafted message is validated by code (citations, stray numbers, as today) and shown to the human, who edits it and confirms before execute runs. Execute sends exactly the confirmed text; the decision audit entry keeps the chosen action, the original draft and the confirmed text. If the draft call fails or its output does not validate, the message step shows no draft and is marked `needs human review` for that output: the human writes the message or chooses another action. No template produces the message (constraint 7).
- **Explain and propose merged into one LLM call.** One structured call returns the explanation with its citations and the proposed action with its justification. Code validates each part as today (citation keys, bracketed references, stray numbers, proposal equal to the policy); a failure in either part routes the case to `needs human review`.
- **Limited passages.** Retrieval still runs and its ranked results are recorded. The passages sent to the model are limited to the finding's own sections (the sections that define the rule, as already used by the stray-number allow-list in ADR-008) and the case's deal memo. Other retrieved passages are not sent.
- **Compact serialization.** Facts, case context and passages are serialized compactly (no indentation, no repeated keys or boilerplate); the system prompt is shared and kept short.

## Consequences

- **Tokens (expected; measured in P1.I2b.S4 before and after):** an approve case makes one call instead of three; a return or escalate case makes two (merged call plus draft). With limited passages and compact input, the target is at most 5,000 tokens per MEAL_PERIOD case, so one case fits within one minute's budget of the default provider, a week ingest needs fewer retries, and the evaluation runs of Iteration 3 cost about half of what three calls per case would.
- **Correctness:** the message always matches the action the human chose; the gap found in the first run cannot occur.
- **Human checkpoint:** still unconditional before execute. For return and escalate the human acts twice (choose the action, then confirm or edit the message); for approve, once. The LLM still has no write path (ADR-009); execute runs only after the human confirms.
- **Demo flow change (demo-script steps 2 and 3):** the case detail shows the explanation, citations and proposal, but no draft. The draft appears when the approver chooses return or escalate; the approver then edits and confirms it. The narration of step 2 drops "and a draft return message"; step 3 becomes "choose Return, review the drafted message, edit, confirm". Step 4 (escalation) shows the escalation note drafted after the approver chooses escalate. `docs/requirements/demo-script.md`, `docs/architecture/overview.md` (state machine, responsibilities table, sequence diagram) and `docs/requirements/customer-workflow.md` where it describes the draft are updated when this record is accepted (P1.I2b.S3).
- **API and UI:** the decide endpoint splits into choosing the action and confirming the message for return and escalate (designed in P1.I2b.S3; the UI in Iteration 4 follows it).
- **Evaluation (ADR-003):** the harness of Iteration 3 simulates the human choosing the expected action so that drafts are produced and judged for return and escalate cases only.
- **Retrieval quality is still measured** on the full ranked results (ADR-017), even though the model sees fewer passages; a governing section missing from the finding's own sections would be a domain error caught by the domain-consistency-validator.
- **Validators:** hitl-workflow-validator PRE before the graph change and GATE after it; grounding-evaluator after the prompt change.

## Implementation design (P1.I2b.S3 and S4)

Written on 2026-10-10 before the graph code changed. The hitl-workflow-validator reviewed a first version PRE (FAIL: five majors, six minors); this version resolves every finding and was reviewed again (results in `docs/progress/iterations/iteration-002b.md`). Author choices recorded the same day: the approver confirms or edits the drafted message before execute; if the draft call fails, the human writes the message and no template is used.

**Nodes and edges.**

```
START -> detect -> (clean: END | findings: retrieve)
retrieve -> (ok: explain_propose | review: needs_human_review)
explain_propose (LLM, one call) -> (ok: validate | review: needs_human_review)
validate (code) -> (ok: human_checkpoint | review: needs_human_review)
needs_human_review (code) -> human_checkpoint
human_checkpoint (interrupt 1: action and actor) -> (approve: execute | return or escalate: draft)
draft (LLM, for the action the human chose) -> validate_draft (code)
validate_draft -> message_checkpoint (always; a failed or invalid draft is not shown)
message_checkpoint (interrupt 2: confirmed message, or cancel) -> (confirmed: execute | cancel: human_checkpoint)
execute (code, the only write path) -> audit (code) -> END
```

- `explain_propose` returns one strict JSON object with an `explanation` part (text, citation keys) and a `proposal` part (action, justification, requested correction, citation keys). It is stored as two suggestions (kinds `explain` and `propose`) from one call, so per-part validation status and the case detail contract stay as they are; one `suggestion` audit entry records the call with both suggestion ids and the token counts.
- `validate` applies to each part exactly what Iteration 2 applied to each output: citation keys (exist, version in force, the case's deal memo, required governing section in the explanation, and cited only from the passages sent), bracketed pseudo-references (S2), stray numbers (ADR-008), proposal equal to the policy action (ADR-009). Any failure routes the case to `needs_human_review` with facts and the reason.
- `human_checkpoint` is unchanged in position and is unconditional. Its resume value is `{action, actor}`; no message is accepted at this step. After the interrupt returns it records in the state the case status at the checkpoint (`awaiting_decision` or `needs_human_review`, re-read from the store at every pass, so a later round after a cancel records it again) for the decision audit entry (S5). For return and escalate it writes a `decision` audit entry with `stage: action_chosen`, the action and the human actor.
- `draft` runs only for return and escalate, with the facts, the case context, the validated explanation (or none when the explanation did not validate), the policy action and the action the human chose. It never runs for approve. Its schema has `for_action`, `recipient_role` (`employee`, `department_head` or `payroll_specialist`), `subject`, `body` and `citation_keys`. The suggestion row and its audit entry are written by the store in one transaction.
- `validate_draft` applies the citation, bracketed-reference and stray-number checks to the subject and the body, and checks that `for_action` equals the human's action and that `recipient_role` fits it (return: employee or department head; escalate: payroll specialist). If the call failed, the output did not parse or did not validate, then (constraint 7) the case is marked `needs_human_review` with the reason prefixed `draft:`, a `review` audit entry records the reason with `facts_only: true`, the draft is not shown, and the graph continues to the message step where the human writes the message or cancels. Code never writes a substitute.
- `message_checkpoint` is a second `interrupt`, with no side effect before it. Its resume value is either `{actor, message, recipient_role?}` with a non-empty message, or `{actor, cancel: true}`. A confirmation must come from the actor who chose the action; a cancel may come from any actor (so a case is never stuck on an absent approver). A cancel writes a `decision` audit entry with `stage: message_cancelled`, the cancelled action, the draft suggestion id and its status, then clears the chosen action, the draft, its suggestion id and its validation from the state and returns to `human_checkpoint`. While the message step is open the case keeps its queue status (`awaiting_decision`, or `needs_human_review` when either the analysis or the draft needs review); the case detail shows `waiting_on: ["message_checkpoint"]`, the chosen action, the validated draft (or none) and its output status.
- **Output status of the draft** is read from the current round's suggestion id held in the state, never from the latest row of that kind: `missing` when the current round has no draft suggestion.
- **Recipient** of a return message comes from the human's resume value or, when omitted, from a code default per action (return: employee). The draft's `recipient_role` is shown to the human as a suggestion; it never sets an execution parameter by itself.
- `execute` sends exactly the confirmed text: the return message for return, the escalation note for escalate. The default escalation note of Iteration 2 is removed; an escalation needs a confirmed message like a return. Approve executes with no message. **Idempotency:** the store's transaction starts with `UPDATE cases ... WHERE id = %s AND status IN ('awaiting_decision', 'needs_human_review') RETURNING id`; when no row returns, nothing is written and execute reports the case as already executed (a retry after a commit whose checkpoint write failed therefore cannot send a second message or add a second pay line).
- `audit` writes the decision entry (`stage: executed`) with the chosen action, the original draft of the final round (validated or not, or none), the confirmed text, whether it was edited, the message source (`draft_confirmed` when the confirmed text equals the draft, `draft_edited` when a draft existed and the text differs, `human_written` when there was no valid draft), the policy action, the proposed action, the number of cancelled rounds and `case_status_before` taken from the last pass through the checkpoint (S5), then the execution entry.

**Resume validation and retries (service).** The service validates every resume value before `Command(resume=...)` (a resume value is persisted with the thread even when the node fails): the action and actor at interrupt 1; at interrupt 2 the actor (equal to the chooser for a confirmation), a non-empty message within the length limit, and `cancel` exclusive with `message`. It checks the waiting node in `snapshot.next`: `decide` while the case waits at the message step, or `message` while it waits at the human checkpoint, is refused with 409 and never treated as an implicit cancel. A stalled thread is retried only with the decision stored in it: when `snapshot.next` is `draft` or `validate_draft`, a repeat of `decide` with the same action and actor resumes it (this repeats the draft call if the LLM call itself was interrupted); when it is `execute` or `audit`, a repeat through `decide` (approve) or `message` (return, escalate) with the same action, actor and confirmed message resumes it; any other submission is refused with 409 naming the stored decision.

**Rules added after the second PRE review (PASS with minors).**

- `decision` audit entries always carry `stage`: `action_chosen` (interrupt 1 for return or escalate), `message_cancelled` (interrupt 2 cancel), `executed` (the executed decision, written with the effects in the `apply_execution` transaction) or `duplicate_attempt` (execute found the case already executed; nothing was written, the request's actor is recorded). Only `executed` stands for an executed decision.
- Each checkpoint node writes at most one audit entry after its interrupt, as its last statement. A thread stalled at a checkpoint node with a pending resume value is resumed by repeating the same request (`invoke(None)`); a different payload gets 409.
- The service serializes resumes per case thread (one lock per thread in the process; the guarded UPDATE remains the guarantee across processes).
- Once a case is marked `needs_human_review` (analysis or draft), it stays so until it is executed; a later valid draft round does not restore `awaiting_decision`.
- `ptc confirm-message` takes `--actor` (default: the catalog's demo approver, as the showcase); the chooser-equality check rejects a mismatch.
- (After the POST code review.) The `executed` decision entry and the `execution` entry are written inside the `apply_execution` transaction, with the effects; the `audit` node only collects their ids, or writes `duplicate_attempt` when execute found the case already executed. A retry after a commit whose checkpoint was lost therefore keeps exactly one `executed` entry.
- (After the POST grounding review.) A citation key written without brackets is validated like a bracketed one, and the drafted message must cite the governing section of every finding, like the explanation.

**API.** `POST /cases/{id}/decide {action, actor}` resumes interrupt 1: approve executes and returns the result; return and escalate run the draft and return the case waiting at `message_checkpoint` with the draft and its output status. This request waits for one LLM call, including the adapter's pacing and retries (seconds to tens of seconds on the free tier); if the client times out after the graph resumed, repeating the same `decide` is handled by the retry rule above. `POST /cases/{id}/message {actor, message, recipient_role?}` or `{actor, cancel: true}` resumes interrupt 2. A message field on `decide` is rejected (422). `GET /cases/{id}` adds `chosen_action` and `waiting_on`.

**Facts (S1).** The engine also provides the meal delay in hours (`hours_late`, MEAL_PERIOD facts schema version 2, derived from `minutes_late`), so the model never converts units (ADR-008); the prompts forbid unit conversion and any number not given.

**Token efficiency (S4).** The retrieve node still records the full ranked results (state and case detail). The passages sent to the model are the finding's own sections (`citation_keys` of each finding) and the case's deal memo; prompts serialize compactly (one-line JSON, passages as plain text, the meaning of each fact listed once per rule instead of once per finding); the system prompt is shared and short. The adapter records input and output tokens per call (already in the call summary); the showcase prints the total per case, and `ptc showcase --dry-run` builds the same prompts offline and prints estimated input tokens per call and per case without any provider call (ADR-019).

**Showcase.** `--decision approve` resumes interrupt 1 and ends. `--decision return` or `escalate` resumes interrupt 1, prints the draft and its status and stops at the message step, so the human reads the draft before accepting it; `--message "..."` (text the human wrote in advance) is the only way to confirm in the same command (recorded as `draft_edited` when a valid draft existed, since it differs from the draft), and it is refused with `--decision approve`. `ptc confirm-message --case <id> [--actor ...] (--accept-draft | --message "..." | --cancel)` resumes the message step; `--accept-draft` is refused when the draft is not valid and adopts the draft's suggested recipient as the human's choice. (Changed after the GATE review: an `--accept-draft` flag on the showcase itself would accept a draft before the human saw it.)
