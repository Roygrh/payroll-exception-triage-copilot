# Evidence profile

Profile: **E3, grounded synthetic problem, synthetic data** (ADR-001).

| Dimension | Status | What this means for readers |
| --- | --- | --- |
| Workflow, fields and statuses | Grounded | Taken from public product documentation of entertainment payroll vendors (onboarding and timekeeping modules), described generically in `sources.md`. The product mirrors the vocabulary: offers, deal memos, timecard events, approval statuses, personal queues, invoice statuses, eligibility tracking. |
| The problem (exception queues are the main operational pain) | Hypothesis | Inferred from the feature set (rejection states, correction loops, bulk approvals, personal queues). To be validated in discovery with real approvers. |
| Volumes and effort | Unknown | No figure for exceptions per week, minutes per exception or cost of a late run exists in this repository. Nothing in the demo or README claims measured impact. |
| Agreement text, rates, penalties | Synthetic | Written for this project. Structure imitates how such agreements are organized; wording and numbers are invented. |
| Eligibility deadline | Real-world parameter | 3 business days after the start date, verified against the public government source on 2026-10-07. Kept real because the scenario needs a credible deadline. |
| Productions, crew, deal memos, timecards | Synthetic | Generated by a seeded generator from the scenario catalog; names invented for this project. |
| Technology facts (tracing vendor regions, checkpointer API, tool configuration) | Verified against vendor documentation | Recorded with dates in the relevant ADRs. |

Rules that follow from the profile:

1. Any statement about customer impact is phrased as a hypothesis until measured.
2. Every assumption is tagged with its origin in `assumptions.md`.
3. The discovery kit (Phase 2) is built from the unknowns above.
