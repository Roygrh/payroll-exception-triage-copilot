# AGENTS.md: working contract for every coding agent in this repository

This file is the portable rulebook. CLAUDE.md imports it; other agent runners read it directly. If anything here conflicts with a tool default, this file wins.

## 1. Hard constraints

These apply to every session, every iteration, every agent (including subagents).

1. **Git is read-only for agents.** Never run a git command that modifies state: add, commit, amend, checkout, switch, stash (push, pop, apply, drop, clear), reset, restore, rebase, merge, cherry-pick, push, pull, fetch, tag creation or deletion, branch creation, rename or deletion, init, clean. Read-only inspection is allowed: status, log, diff, show, blame, stash list, stash show, branch and tag listing, rev-parse, ls-files. This holds for the `-C <path>` and `-c <key>=<value>` forms, for commands wrapped in `sh -c`, and for chained commands. The author commits by hand. A PreToolUse hook enforces this (ADR-014); do not try to work around it.
2. **No AI attribution anywhere.** No co-author trailers, no "generated by" notes, no mention of AI assistants or AI coding tools in any repository file, commit message or pull request text.
3. **No real brands.** Product, code, data and documentation must not name any real company, product, union, guild, studio, staffing firm or person from the entertainment payroll domain or from the project's private inputs. The domain is generic "entertainment production payroll"; every organization, agreement, production and person is fictitious. Technology vendors named in accepted ADRs (the LLM provider, the tracing vendor, databases, frameworks, cloud provider) are allowed because they are part of the stack, not of the domain.
4. **English only.** All repository content, including comments, data and commit messages, is in English.
5. **No em dashes** in any repository file. Use colons, commas, parentheses or periods.
6. **No copied text from real collective agreements.** Agreement text, rates, penalty tables and deadlines are synthetic (one exception, documented in ADR-001: the employment eligibility verification deadline mirrors the public government rule because the scenario needs a real-world deadline).
7. **The LLM is the central engine.** Explanation, resolution proposal and return-message drafting are always produced by the LLM. No iteration may replace these steps with deterministic templates or rules. If the LLM call fails, or its citations do not validate, the case is marked `needs human review`. There is no silent deterministic fallback.
8. **Stay inside this repository folder.** Never read, search or write outside it (the session scratchpad for temporary files is the only exception). If something you need is missing, stop and report.

Supporting constraints:

- The LLM never computes (ADR-008). Hours, minutes, increments and amounts come from the rule engine as structured input.
- The LLM has no write path (ADR-009). Only code executes actions, and only after the human checkpoint.
- The author's private inputs are gitignored and are never referenced from a committed file except `.gitignore`. Nothing from them is copied into the repository: no names, phone numbers, compensation figures or brand names.
- Any new third-party service or dependency requires an ADR before use.
- When a shell command must contain prose about git (for example writing documentation through a heredoc), prefer the file-writing tool over the shell. The guard hook reads shell commands only and fails closed on anything that looks like a git invocation.

## 2. Authority hierarchy

When documents disagree, the higher one wins and the lower one must be corrected in the same iteration:

1. Hard constraints in this file.
2. Accepted ADRs in `docs/decisions/` (a newer accepted ADR wins over an older one it supersedes; superseding must be explicit).
3. `docs/requirements/project-brief.md` (the brief with ADR changes applied).
4. `docs/requirements/demo-script.md` (governs Phase 1 scope: if a component is not in the script, it is not built in Phase 1).
5. `docs/requirements/domain-model.md` and `docs/requirements/customer-workflow.md`.
6. `docs/architecture/overview.md`.
7. `docs/planning/current-plan.md` (`initial-plan.md` is frozen history, never rewritten).
8. `docs/progress/current-state.md` and iteration logs.
9. Code, data and tests.

A decision that changes any of 2 to 6 requires a new ADR (MADR style: context, decision, consequences, status) and an entry in `docs/decisions/README.md`.

## 3. Execution loop (every working session)

1. **Orient.** Read `docs/progress/current-state.md` (Handoff block first), then the step you are about to execute in `docs/planning/current-plan.md`, then the ADRs that step cites.
2. **Confirm scope.** The step's objective, artifact, acceptance condition and required validation are the contract. Do not widen it. If the step is blocked, record why in the iteration log and stop.
3. **Run PRE validators** when the step touches the workflow graph or the action path: `hitl-workflow-validator`.
4. **Build.** Tests first where practical. Parameters come from `data/rule-parameters.yaml` (ADR-007); never hard-code a domain number elsewhere.
5. **Run POST validators** required by the step: `test-engineer` for code, `code-reviewer` for any code change, `grounding-evaluator` after retrieval or prompt changes (gate), `domain-consistency-validator` after data or corpus changes, `hitl-workflow-validator` as gate before any iteration that ships the graph.
6. **Self-check before handing off:** no em dashes, no real brands, no AI attribution, English only, no file outside the repository touched, no git state modified.
7. **Record.** Update `docs/progress` (section 5) and, if the plan changed, `docs/planning/current-plan.md` with a dated "Plan changes" entry.
8. **Hand off.** Rewrite the Handoff block in `current-state.md`: done, next, open decisions. Do not commit.

## 4. Definition of done

A step is done when all of the following hold:

- The artifact named in the plan exists at the named path.
- The acceptance condition is demonstrably met (a command, a test or a reviewer output shows it).
- Every required validator returned `PASS` (a `FAIL` or `BLOCKED` must be resolved or explicitly accepted by the author in an ADR or in the iteration log).
- Deterministic tests pass; the evaluation gate passes where the step requires it (ADR-003).
- Documentation that the step changes (requirements, architecture, ADRs, plan, progress) is updated in the same step.
- The repository scans clean: no forbidden terms (the author keeps the term list outside version control and runs the scan before committing), no em dashes, no AI attribution, no private data.
- No git state was modified by an agent.

An iteration is done when all its steps are done, its demo-script steps (if any) can be rehearsed, and `docs/progress/iterations/iteration-NNN.md` exists.

## 5. How to update docs/progress after each iteration

1. Create `docs/progress/iterations/iteration-NNN.md` (three digits) with these sections: Summary; Steps completed (step id, artifact, acceptance evidence, validators run with status); Deviations from the plan (and the ADR or plan-change entry that records each); Validator findings carried forward; Metrics (test counts, eval pass rates, gate status) when they exist; Open decisions raised.
2. Rewrite `docs/progress/current-state.md` top to bottom. The file always starts with a `## Handoff` block containing exactly three lists: **Done** (cumulative, one line per iteration plus the last few steps), **Next** (the single next step id and what it needs), **Open decisions** (each with an owner and the ADR it would produce). Below the handoff: current phase and iteration, what runs today (commands), known gaps, and risks.
3. If the plan changed, append a dated entry to the "Plan changes" section at the end of `docs/planning/current-plan.md` and edit the affected steps in place. Never edit `docs/planning/initial-plan.md`.
4. If a decision was taken, add the ADR and index it in `docs/decisions/README.md`; set superseded ADRs to `Superseded by ADR-NNN`.
5. Update `docs/evidence/assumptions.md` when an assumption was confirmed, refuted or added (tag it with its origin).
6. Leave the working tree for the author to inspect and commit. Report what changed, what was validated and what remains open.

## 6. Subagents

Definitions live in `.claude/agents/`. Each has one responsibility, minimal tools and the same output format: `status: PASS | FAIL | BLOCKED`, then findings, each with severity (`blocker`, `major`, `minor`, `info`), evidence, location and recommendation.

| Agent | When | Role |
| --- | --- | --- |
| `test-engineer` | POST, after code changes | Runs the test suites, reports failures with evidence |
| `code-reviewer` | POST, after code changes | Read-only review for correctness, constraints and ADR conformance |
| `grounding-evaluator` | POST after retrieval or prompt changes, GATE | Runs evals; verifies citations exist, match the effective version and support the claim |
| `hitl-workflow-validator` | PRE before graph or action changes, GATE before shipping | Read-only: LLM has no write path, every action passes the human checkpoint, no deterministic fallback |
| `domain-consistency-validator` | POST after data or corpus changes | Read-only: YAML, agreement, rule engine and eval cases agree; no real brands; no copied agreement text |

## 7. Conventions

- Python 3.12, FastAPI, LangGraph, PostgreSQL 16 with pgvector; React with TypeScript and Vite; OpenTelemetry with the tracing vendor named in ADR-004; Docker compose for local runs.
- Citation key format: `CGMA-2026.1-8.2` (agreement code, version, section).
- Rule ids are upper snake case (`MEAL_PERIOD`). Scenario ids are `SC-NN`. Deal memo ids are `DM-NN`. Eval case ids are `EV-NN`.
- Dates are ISO 8601. Times of day in timecards are decimal hours from midnight of the shift date (a wrap at 26.5 is 02:30 the next calendar day).
- Money is USD with two decimals; amounts are computed by code only.
